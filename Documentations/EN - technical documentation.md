## 3. File Structure and Configuration

The application is portable. All configuration and log files are stored in the folder where the `EasySave.exe` executable is located.

### General Configuration (`config.json`)
- **Location**: `<Application_Folder>/EasyLogs/config.json`
- **Global Parameters**:
  - `LogFormat`: Write format for log files (`Json` or `Xml`).
  - `Language`: Console interface language (`en` or `fr`).

### Job Configuration (`jobs.json`)
- **Location**: `<Application_Folder>/EasyLogs/jobs.json`
- **Format**: JSON array of `BackupJob` objects (Name, Source, Target, Type).
- **Business Rule**: Technically limited to a maximum of 5 jobs. If this file is deleted, the list will be empty on the next launch.

### Activity Logs (`DailyLog_{date}`)
- **Location**: `<Application_Folder>/EasyLogs/DailyLog_{dd_MM_yyyy}.json` (or `.xml`)
- **Format**: One file per day generated by the `EasyLog` DLL.
- **Content**: Details of each transfer (`Timestamp`, `Name`, `Source`, `Target`, `FileSize`, `TransferTimeMs`).

### Real-time State File (`state.json`)
- **Location**: `<Application_Folder>/EasyLogs/state.json` (or `.xml`)
- **Content**: Progress state of the current job (`Progression`, `TotalFilesToCopy`, `NbFilesLeftToDo`, `RemainingFilesSize`, `State`).
- **Behavior**: Dynamically rewritten at each file transfer.

## 4. Architecture and Technical Design

### Folder Structure (Console Architecture)
The application is divided into namespaces ensuring loose coupling:

* **`EasySave.Models`**: Data structures (`BackupJob`, `BackupType`).
* **`EasySave.Services`**: Business logic and orchestration (`JobManager`, `BackupEngine`).
* **`EasySave.Patterns.Strategy`**: Backup algorithms (`FullBackupStrategy`, `DifferentialBackupStrategy`).
* **`EasySave.Patterns.Factory`**: Software creation factories (`BackupFactory`).
* **`EasySave.Patterns.Bridge`**: OS file system abstraction (`IFileSystem`, `LocalFileSystem`).
* **`EasySave.Patterns.Observer`**: Real-time tracking listener (`IBackupObserver`, `StateLoggerObserver`).
* **`EasyLog` (DLL)**: External logging library (Manages daily log files and live state).

### Design Patterns Implementation

| Pattern | Technical problem solved | Solution provided in the architecture |
| :--- | :--- | :--- |
| **Strategy** | Avoid polluting the backup engine with complex mathematical algorithms. | Encapsulation of each algorithm (`Full`, `Differential`) in its own class via the `IBackupStrategy` interface. |
| **Observer** | Update `state.json` in real time without making the engine dependent on the log system. | The engine "broadcasts" its state (`NotifyObservers`). `StateLoggerObserver` listens and writes without impacting the engine. |
| **Singleton** | Avoid concurrent access crashes (File Lock) when writing log files. | The `Logger` class guarantees a single instance secured by a locking mechanism (`lock`). |
| **Factory** | Simplify the instantiation of strategies without multiplying `if/switch` statements in the engine. | `BackupFactory` dynamically generates and returns the correct algorithm based on the type requested by the user. |
| **Bridge** | Allow unit testing without creating real physical files on the hard drive. | Creation of an `IFileSystem` interface acting as a bridge, allowing the injection of "Mocks" during the testing phase. |

### Compliance with SOLID Principles

The application's architecture was designed to guarantee robust, unit-testable code ready to evolve towards graphical interfaces (for Deliverable 2) without rewriting the core engine:

- **S - Single Responsibility**: Each file has a strict role. `JobManager` manages the list, `BackupEngine` orchestrates the copying, `Logger` manages writes.
- **O - Open/Closed**: If we need to add a new backup type (e.g., Incremental), we do not have to modify `BackupEngine`, but simply create a new class implementing `IBackupStrategy`.
- **L - Liskov Substitution**: The `BackupEngine` expects to receive an `IBackupStrategy`. Whether it is a `FullBackupStrategy` or a `DifferentialBackupStrategy`, the engine uses it in exactly the same way without any anomalies.
- **I - Interface Segregation**: Our interfaces are small and targeted. `IBackupObserver` only contains the `Update()` method, `IBackupStrategy` only contains `GetFilesToCopy()`.
- **D - Dependency Inversion**: `BackupEngine` (high level) no longer depends directly on `System.IO.File` (low level), but on the `IFileSystem` abstraction.

## 5. Integrity and Tests (Quality Assurance)

We have placed great importance on code quality. The **`EasySaveTest`** (xUnit) solution covers the critical aspects of the v1.0 engine:

- **Model Tests (`BackupJobTests`)**: Verifies that the instantiation of a job correctly sets the name, directories, and type in memory.
- **Architecture Tests (`BackupFactoryTests`)**: Ensures that the software factory returns the correct business object (`Full` or `Differential`) according to the provided parameter.
- **Concurrency Tests (`LoggerTests`)**: Proves that the Singleton pattern strictly returns the same memory instance on each call to prevent any write conflicts.
- **Business Rule Tests (`JobManagerTests`)**:
  - Validation of adding/removing jobs via index.
  - Creation of six consecutive jobs to prove the technical block beyond the **strict limit of five jobs**.
  - Maintenance of stability (anti-crash) when attempting to delete with an out-of-bounds index.
- **Resilience Tests (`BackupEngineTests`)**: Verifies that the engine stops cleanly and securely (without a fatal error) if the provided source directory is physically not found.

The goal of this coverage is to validate the technical foundations (v1.0) before tackling the migration to a graphical interface.
