## 3. File Structure and Configuration

The application is portable. All configuration and log files are stored in the folder containing the `EasySaveApp.exe` executable.

### General Configuration (`config.json`)
- **Location**: `<Application_Folder>/config.json`
- **Global Parameters (V2.0 Evolution)**:
  - `LogFormat`: Log file writing format (`.Json` or `.Xml`).
  - `Language`: Interface language (`en` or `fr`).
  - **`BusinessSoftware`**: Name of the business executable (e.g., `calculator.exe`) that prohibits backup execution.
  - **`ExtensionsToEncrypt`**: List of file extensions (e.g., `.txt; .pdf`) requiring encryption via third-party software.
  - **`CryptoKey`**: Encryption key used by CryptoSoft.

### Job Configuration (`jobs.json`)
- **Location**: `<Application_Folder>/jobs.json`
- **Format**: JSON array of `BackupJob` objects (Name, Source, Target, Type).
- **Business Rule (V2.0 Evolution)**: The historical technical limit of 5 jobs has been **removed**. Users can now create and manage an unlimited number of jobs.

### Activity Logs (`DailyLog_{date}`)
- **Location**: `<Application_Folder>/EasyLogs/DailyLog_{dd_MM_yyyy}.json`
- **Format**: One file per day generated by the `EasyLog` DLL in JSON or XML.
- **Content (V2.0 Evolution)**: Details of each transfer (`Timestamp`, `Name`, `Source`, `Target`, `FileSize`, `TransferTimeMs`, and now **`EncryptionTimeMs`**).

### Real-time State File (`state.json`)
- **Location**: `<Application_Folder>/EasyLogs/state.json`
- **Content**: Progress status of the current job (`Progress`, `TotalFilesToCopy`, `NbFilesLeftToDo`, `RemainingFilesSize`, `State`).
- **Behavior**: Dynamically rewritten at each file transfer.

## 4. Architecture and Technical Design

Version 2.0 marks the transition from a sequential architecture (Console) to an event-driven graphical architecture, structured around the MVVM pattern.

### MVVM Structuring and Folders
The application is divided to guarantee a strict separation between the visual interface and business logic:

* **`Models`**: Data structures (`BackupJob`). They now integrate `ObservableObject` to notify the interface of changes (e.g., progress bar updates).
* **`Views`**: `.axaml` files managing display only (Avalonia UI).
* **`ViewModels`**: Orchestrators (e.g., `MainWindowViewModel`) binding views to services via *DataBinding* and commands (`ICommand`).
* **`Services`**: Core business logic (`JobManager`, `BackupEngine`, `EncryptionService`).
* **`Patterns`**: `Strategy`, `Factory`, `Bridge`, `Observer`, `Singleton` (Managing the underlying software architecture).

### New Business Features (v2.0)

**1. Business Software Interruption**
Before starting and *during* the copy loop of each file, the `BackupEngine` checks if the process defined in `BusinessSoftware` is running. If so, the backup stops immediately (`INTERRUPTED` state) and logs the anomaly.

**2. On-the-fly Encryption (CryptoSoft)**
When a file is copied, the engine compares its extension with the `ExtensionsToEncrypt` list. If it matches, it calls the `EncryptionService` to encrypt the target file while measuring the execution time (`EncryptionTime`), which is then recorded in the daily logs.

### Design Pattern Implementation

The architecture was designed to ensure robust, scalable, and testable code. Patterns from v1.0 were retained and adapted to the new graphical environment.

#### 1. Singleton: Securing File Access (Thread-Safety)
* **Technical Problem:** Managing concurrent writes (logs and states), a critical aspect with an asynchronous UI.
* **Solution:** The Singleton (`Logger`), combined with a `lock` mechanism, acts as a secure bottleneck: all write requests are processed sequentially.

#### 2. Observer: Decoupling the Engine from the Interface and Logs
* **V2.0 Evolution:** The engine still "broadcasts" its progress. The key innovation is that this notification updates the `Progress` property of the `BackupJob` object. Thanks to MVVM DataBinding, the GUI (progress bar) refreshes automatically, while the engine remains completely unaware of the UI's existence.

#### 3. Strategy: Isolating Algorithmic Logic
* **Solution:** Each calculation algorithm (Full/Differential) is encapsulated. The engine simply requests the list of files to copy from the strategy without worrying about internal logic (Open/Closed Principle).

#### 4. Factory: Centralizing Object Creation
* **Solution:** The Factory analyzes the backup type requested by the user from the interface and dynamically instantiates the appropriate tool (`Full` or `Differential`).

#### 5. Bridge / (Dependency Inversion): Making the System Testable
* **Solution:** Creation of an `IFileSystem` interface acting as an abstraction. In production, the engine uses the actual disk. During the testing phase (xUnit), we inject "Mocks" in RAM, ensuring fast and safe tests without affecting the OS.

### Compliance with SOLID Principles

- **S - Single Responsibility**: `JobManager` manages the list, `BackupEngine` orchestrates the copy, `EncryptionService` handles encryption.
- **O - Open/Closed**: New backup types can be added (e.g., Incremental) without modifying `BackupEngine`.
- **L - Liskov Substitution**: `BackupEngine` handles all strategies identically without anomalies.
- **I - Interface Segregation**: Small, focused interfaces (`IBackupObserver`, `IBackupStrategy`).
- **D - Dependency Inversion**: `BackupEngine` depends on `IFileSystem` (abstraction) rather than `System.IO.File`.

## 5. Integrity and Testing

The coverage of the **`EasySaveTest`** solution (xUnit) was adapted and expanded to validate the technical foundations of V2.0:

- **Model Testing (`BackupJobTests`)**: Verifying the persistence of the graphical state (`Progress` and `ShowProgress`).
- **Business Rule Testing (`JobManagerTests`)**:
  - **Evolution:** Removal of the legacy test limiting the system to 5 jobs.
  - Added a test for the `UpdateJob()` method ensuring that modifications to an existing job are saved correctly.
- **Resilience Testing (`EngineFaultToleranceTests`)**: Ensures the engine properly handles user input errors from the interface (e.g., source path not found) by capturing the exception (`Record.Exception`) instead of causing an application crash.
- **Interruption Testing**: Validation of business process detection prohibiting or interrupting a backup on-the-fly.
- **Architecture Testing (`LoggerTests` & `BackupFactoryTests`)**: Strict maintenance of Singleton and Factory validation.
